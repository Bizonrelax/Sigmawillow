<summary><b>ЧАСТЬ 0. РУКОВОДСТВО ВЛАДЕЛЬЦА — читать человеку, боту не исполнять</b></summary>

### 0.1 Что это за файл

Это **инструкция для кодеров, а не для тебя**. Один файл, который лежит в Sigmawillow и обслуживает все твои репозитории сразу — и существующие, и те, что ты создашь потом.

**Зачем он нужен.** Ты запускаешь несколько Гвк в разных вкладках. Без правил они берут одну и ту же задачу, портят друг другу файлы и спрашивают тебя о том, что должны решить сами. Этот файл превращает их в самостоятельную бригаду: каждый сам узнаёт, что делать, сам берёт свободный кусок работы, сам отчитывается, а последний сам собирает результат и убирает за собой.

**Что он даёт тебе:**
- ты не помнишь ни номеров, ни ролей, ни количества кодеров — они узнают всё сами;
- ты не разбиваешь ТЗ на части — это делает первый кодер;
- ты не создаёшь pom.xml, workflow, .gitignore и README — это делает первый кодер по готовым шаблонам;
- ты не сливаешь ветки и не удаляешь мусор — это делает последний кодер;
- твоё участие: одна строка в чат и взгляд на одну страницу состояния.

**Чего он не делает:** не заменяет ТЗ, не придумывает требования, не проверяет Windows-GUI в Linux-песочнице (это уходит в GitHub Actions), не задаёт тебе вопросов.

**Как устроен файл:** Часть 0 — эта справка, для тебя. Части 1–12 — машинные инструкции, для бота. Ты можешь читать только Часть 0 и никогда не открывать остальное.

### 0.2 Один раз в жизни

Положи этот файл в `Bizonrelax/Sigmawillow` по пути `GVK/PROTOCOL.md` (GitHub → Add file → Create new file). Всё. Для каждого нового проекта подготовки не требуется.

### 0.3 Каждый запуск

Новый чат, селектор ветки — `main`. В сообщение:

```
Токен: ghp_XXXX
Репозиторий: Bizonrelax/Milkromug
ТЗ: Docs/TZ-Milkromug.md
Прочитай GVK/PROTOCOL.md из Bizonrelax/Sigmawillow и действуй по нему.
```

Строку `ТЗ:` можно не писать — кодер найдёт ТЗ сам. Сколько кодеров запускать — решаешь ты, протокол подстроится. По умолчанию один кодер берёт один фрагмент; хочешь меньше запусков — рычаг `СЕРИЯ`.

### 0.4 Команды-рычаги

Дописываются к тому же сообщению. Без команды — обычный цикл.

| Команда | Действие |
|---|---|
| **ПАМЯТКА** | вывести эту таблицу в чат, чтобы ты не запоминал |
| **ТОЛЬКО ОТЧЁТ** | ничего не менять, дать сводку |
| **СЕРИЯ** | брать фрагменты подряд, пока хватает квоты |
| **ЖДИ 6** | ждать освобождения до 6 часов (по умолчанию 2) |
| **ПРОДОЛЖИ 007** | подхватить зависший фрагмент, продлить аренду |
| **ОТОЗВАТЬ 007** | поколение +1, начать фрагмент заново |
| **ОТОЗВАТЬ ДОЛГИЙ** | то же для самого долгого фрагмента |
| **ОСВОБОДИ 007** | снять захват без переделки |
| **ЗАКРОЙ** | принудительно закрыть ТЗ: слияние, тесты, уборка |
| **ПЕРЕПЛАНИРУЙ** | пересобрать план; только когда живых захватов нет |
| **ОБНОВИ ВЕРСИИ** | поднять пинованные версии плагинов и actions, проверить сборку |

### 0.5 Что делать по последней строке отчёта

| Видишь | Делаешь |
|---|---|
| ЗЕЛЕНО / ПУБЛИКОВАТЬ | запускаешь следующего той же строкой |
| КРАСНО / НЕ ПУБЛИКОВАТЬ | новый чат: `ПРОДОЛЖИ NNN` |
| «Свободных нет, захваты живые» | запускаешь позже или `ЖДИ` |
| «Все закрыты, отчёты положительные» | новый чат — он закроет ТЗ сам |
| «FINAL.md создан» | работа окончена, никого не запускать |
| «План создаётся другим» | запустить через минуту |

### 0.6 Куда смотреть глазами

`GVK/STATE.md` в целевом репозитории — одна страница, вся картина. Больше ничего открывать не нужно.

### 0.7 Чего не делать

Не создавать ветки руками. Не править `PLAN.md` руками. Не нажимать кнопки слияния GitHub. Не давать `ПЕРЕПЛАНИРУЙ` при живых захватах. Не писать токен в файлы репозитория.

### 0.8 Частые вопросы

**Я уже навертел исходники вручную — их выбросят?** Нет. Первый кодер обязан провести аудит и по умолчанию сохранить всё рабочее. Переписывание — только с доказательством поломки, удаление — только с доказательством, что код никем не используется. Все удаления происходят в ветке и обратимы через историю git.

**Подойдёт для любого моего репозитория?** Да. Стек един: Java 21, Maven, переносимый EXE через jpackage. Он применяется всюду, где создаётся программа. В чисто документном репозитории каркас не создаётся — там проверяются шапки md+ и ссылки.

**Нужен Windows-EXE.** Он собирается на раннере GitHub Actions `windows-latest`, потому что jpackage собирает Windows-пакет только на Windows. Готовый ZIP лежит в Releases и артефактах, в git не коммитится.

**Бот умер молча.** Ничего не потеряно: в ветке лежат только зелёные состояния. Аренда истечёт через 80 часов, либо ты дашь `ОСВОБОДИ` / `ПРОДОЛЖИ`.

**Сменилась модель.** Протокол от модели не зависит: всё состояние в файлах, а не в памяти чата.

**Что значит «версии пинованы».** Версии плагинов и actions прибиты к конкретным числам, чтобы сборка не ломалась сама собой. Поднимать — только рычагом `ОБНОВИ ВЕРСИИ`.

# ЧАСТЬ 1. ОБЩИЕ ПРАВИЛА КОДЕРА

**Часть 0 — справка для человека. Не исполнять, не учитывать при планировании. Твои инструкции начинаются здесь.**

1.1. Ты — Гвк. Работаешь автономно. **Вопросов владельцу не задавать никогда.** При неоднозначности применяй правило выбора по умолчанию и фиксируй решение в `GVK/AUDIT.md`. Если действие невозможно — отчёт с причиной и выход.

1.2. Источник истины — файлы `GVK/claims/*.md`. `STATE.md` — производная сводка; при расхождении верь захватам.

1.3. Токен: только в переменной окружения и заголовках. Не писать в файлы, `.git/config`, историю команд, отчёты. В отчётах маскировать до последних 4 знаков.

1.4. Бутстрап первой командой:
```bash
[ -f /workspace/env.sh ] || cat > /workspace/env.sh <<'EOF'
export JAVA_HOME=/opt/jdk-21
export PATH=$JAVA_HOME/bin:$PATH
export GH_TOKEN='<из сообщения владельца>'
EOF
source /workspace/env.sh
```
Далее только `source /workspace/env.sh`. Заново окружение не исследовать.

1.5. Тип репозитория и критерий готовности определяй сам:

| Найдено | Тип | Готовность |
|---|---|---|
| ТЗ на программу, либо `*.java`, либо `pom.xml` | программный | Часть 10 (стек Java 21 / Maven / jpackage), затем `mvn -B -ntp verify` → Failures: 0, Errors: 0 |
| `*.py` без ТЗ на Java-программу | скриптовый | `pytest -q` → все пройдены |
| только `*.md`, `*.ipynb`, данные | документный | шапки md+ валидны, относительные ссылки существуют; каркас не создавать |

Целевая платформа: **Java 21, Windows 11**. Ассемблер — единственная допустимая альтернатива Java, только по прямому указанию ТЗ. Базы данных не вводить: данные только в обычных файлах, переносимость копированием папки.

1.6. Развилка по состоянию репозитория:
- `GVK/PLAN.md` отсутствует → ты первый, иди в Часть 2;
- план есть → иди в Часть 3;
- план создаётся другим (отказ 422 при попытке создать) → читать готовый, идти в Часть 3;
- `GVK/FINAL.md` существует → отчёт «ТЗ закрыто», выход.

1.7. ТЗ искать в порядке: имя из сообщения владельца → `Docs/ТЗ*.md` → `TZ*.md`, `SPEC*.md` → `README.md` → единственный `.md` с разделами требований. Несколько кандидатов → выбрать наибольший по объёму, выбор зафиксировать в `PLAN.md`. ТЗ не найдено вовсе → отчёт и выход.

# ЧАСТЬ 2. ПЕРВЫЙ КОДЕР

2.1. **Атомарно создай `GVK/PLAN.md`** (PUT без `sha`). Отказ 422/409 → план уже создаёт другой, переходи к 3.1.

2.2. **Аудит наследия.** Прочитай ТЗ. Составь инвентарь всех исходников. Зафиксируй базовую линию: собирается ли проект, какие тесты падают. Каждому существующему файлу присвой вердикт в `GVK/AUDIT.md`:

| Вердикт | Когда | Доказательство |
|---|---|---|
| KEEP | соответствует ТЗ или не противоречит | по умолчанию, обоснование не требуется |
| REFACTOR | рабочее, но мешает границам фрагментов | что именно мешает |
| REWRITE | противоречит ТЗ или сломано | падающий тест или трассировка |
| DELETE | мёртвый код | вывод grep: ссылок нет; в ТЗ не упомянут |

Правило: **сохраняй лучшее, убирай худшее, не переписывай по вкусу.** Отсутствие доказательства = KEEP. Все удаления — только в ветке фрагмента.

2.3. **Фрагментация.** Граница фрагмента = граница пакета/каталога, пересечений файлов нет. Размер: 5–15 файлов, ориентир один сеанс. Число фрагментов ≈ ceil(число исходников / 10), округляя вверх до границ пакетов. Каждый фрагмент получает: номер, пакеты, задачи из ТЗ, наследие (файлы и вердикты), критерий готовности точной командой, оценку часов, метку `ci: windows` при необходимости Windows-сборки или GUI.

2.4. **Реестры.** `GVK/PORTS.md` — публичные сущности (поля, объекты, методы, константы, форматы файлов), на которые ссылаются из других пакетов: имя, сигнатура, владелец-фрагмент, зависимые. `GVK/LINKS.md` — направленные связи «фрагмент → порт → фрагмент», задающие порядок слияния. `GVK/REQUESTS.md` — заявки на изменение чужого порта. TCP-порты для локального запуска раздай по фрагментам (8081, 8082, …) и запиши в `PLAN.md`.

2.5. **Фрагмент 000 — каркас проекта.** Выполни Часть 10 и Часть 11 (скелет README). Если каркас уже есть — сверь с шаблонами, дополни недостающее, расхождения запиши в `AUDIT.md`.

2.6. Запиши `PLAN.md`, `AUDIT.md`, `PORTS.md`, `LINKS.md`, `REQUESTS.md`, `STATE.md`, каркас и README, пуш в `main`. Отчёт по Части 5. Выход. Фрагменты разработки в этой сессии не брать.

# ЧАСТЬ 3. ЗАХВАТ ФРАГМЕНТА

3.1. Прочитай `GVK/PLAN.md` и все `GVK/claims/*.md`.

3.2. Выбери фрагмент: свободный → самый долгий по оценке → при равенстве меньший номер. Просроченная аренда (`lease_until` в прошлом) считается свободной. Рычаг владельца перекрывает этот порядок.

3.3. **Атомарный захват:**
```bash
PUT /repos/OWNER/REPO/contents/GVK/claims/NNN.md
{"message":"claim NNN","content":"<base64>"}   # поле sha НЕ указывать
```
201 → фрагмент твой. 422 или 409 → занят, вернись к 3.2 со следующим.

3.4. В захвате укажи: `owner`, `epoch`, `lease_until` (сейчас + 80 часов), `packages`, `branch`. **Поколение (epoch)** — счётчик отзыва. При возобновлении продлевай аренду (heartbeat).

3.5. Клонируй, создай ветку `gvk/NNN` от `origin/main`. Вся работа только в ней.

3.6. Свободных фрагментов нет:
- есть живые захваты → режим ожидания (Часть 6);
- все захваты закрыты и все отчёты положительные → закрытие ТЗ (Часть 7);
- все закрыты, но есть отрицательный отчёт → отчёт о блокере, выход.

# ЧАСТЬ 4. РАБОТА НАД ФРАГМЕНТОМ

4.1. Прочитай `GVK/reports/NNN.md`, если есть — там записка предшественника: что сделано, где остановился, что не проверено. Начни с последнего зелёного коммита ветки.

4.2. Наследие фрагмента обрабатывай по вердиктам `AUDIT.md`. Сначала приведи фрагмент к зелёному baseline, потом добавляй новое.

4.3. Микро-шаги. После каждой правки — компиляция. После шага — точечный тест. Полный набор — на чек-поинте.

4.4. **Зелёный чек-поинт → коммит и пуш немедленно.** Коммит — страховка, а не финал. **Красное не пушить никогда.** В ветке существуют только зелёные состояния.

4.5. Красный после микро-фикса → трассировка с печатью стадии, вывод в отчёт. Архитектуру без трассировочного доказательства не менять. Для бага сначала падающий регрессионный тест, потом лечение.

4.6. **Перед каждым пушем** проверь поколение:
```bash
git fetch origin main
git show origin/main:GVK/claims/NNN.md
```
`epoch` не совпадает с твоим → работу выбросить, отчёт «захват отозван», выход.

4.7. Трогай только файлы своих пакетов. Чужой порт менять нельзя — оставь заявку в `GVK/REQUESTS.md`. `PLAN.md` не менять: это право первого и закрывающего кодера.

4.8. Фрагмент с `ci: windows` проверяй через GitHub Actions на `windows-latest`. Локально Windows-пакет не собирать.

4.9. Меняешь видимое пользователю поведение — обнови соответствующий раздел README **в обеих языковых частях, в том же коммите**.

4.10. Осталось ~3 вызова до лимита → зафиксировать зелёное, написать отчёт с запиской о недоделанном, освободить захват, выход.

# ЧАСТЬ 5. ЗАВЕРШЕНИЕ ФРАГМЕНТА И ОТЧЁТ

5.1. Пуш зелёного в `gvk/NNN`. Создай `GVK/reports/NNN.md`: статус, ветка, хэш последнего зелёного, числа тестов, что осталось (записка следующему). Обнови `GVK/STATE.md` (при 409 — перечитать и перезаписать один раз; не удалось — пропусти, истина в захватах). Удали `GVK/claims/NNN.md`. Один пуш в `main`.

5.2. Отчёт в чат — **не более 30 строк**, таблицей шаг → статус → хвост вывода, с хэшами коммитов. Обязательная строка:

```
ФРАГМЕНТЫ: занято A | свободно B | готово к слиянию C | всего D; самый долгий: NNN (T ч)
```

Последние две строки строго:
```
СОСТОЯНИЕ: ЗЕЛЕНО|КРАСНО (tests: пройдено/всего, skipped Z)
ВЕРДИКТ: ПУБЛИКОВАТЬ|НЕ ПУБЛИКОВАТЬ — причина ≤10 слов
```

5.3. Рычаг `СЕРИЯ` и квота позволяет → вернись к 3.1. Иначе выход.

# ЧАСТЬ 6. ОЖИДАНИЕ

Опрашивай `GVK/STATE.md` раз в 10 минут. Потолок 12 опросов (2 часа), рычаг `ЖДИ N` поднимает до N часов. Появился свободный фрагмент → Часть 3. Потолок достигнут → отчёт и выход.

# ЧАСТЬ 7. ЗАКРЫТИЕ ТЗ

7.1. Условия: свободных фрагментов нет, живых захватов нет, все отчёты положительные. Иначе — отчёт и выход.

7.2. Сливай ветки **в порядке из `GVK/LINKS.md`**: сначала владельцы портов, потом зависимые. Обработай заявки `REQUESTS.md`. После каждого слияния — полный набор тестов.

7.3. Красное на слиянии → слияние откатить, отчёт о блокере с указанием ветки и вывода, выход. ТЗ не закрывать.

7.4. Доведи README до полного соответствия реальному поведению программы (Часть 11.4).

7.5. Зелёное → удали все ветки `gvk/*` на remote, удали `GVK/claims/*`, обнови `STATE.md`, создай `GVK/FINAL.md` с итогом.

7.6. **Чистый финиш.** В отчёте явно напиши: «Ветки удалены, слияние выполнено. Любые кнопки слияния или синхронизации, которые показывает UI GitHub, недействительны, нажимать их не нужно».

# ЧАСТЬ 10. КАРКАС ПРОЕКТА (фрагмент 000)

## 10.1 Когда создавать

Тип репозитория определён в 1.5. Для программного репозитория стек един: **Java 21, Maven, переносимый EXE через jpackage app-image**. Spring Boot добавлять только если ТЗ требует HTTP-интерфейс; по умолчанию — чистая Java.

Имена: `artifactId` = имя репозитория в нижнем регистре, только `[a-z0-9]`. Пакет = `io.github.bizonrelax.<artifactId>`. Главный класс = `Main`.

Существующие файлы каркаса **не перезаписывать вслепую**: сверь с шаблоном, дополни недостающее, расхождения зафиксируй в `GVK/AUDIT.md`.

## 10.4 .github/workflows/maven.yml

```yaml
name: maven

on:
  push:
    branches: [ main ]
    tags: [ 'v*' ]
  pull_request:
    branches: [ main ]
  workflow_dispatch:

permissions:
  contents: write

concurrency:
  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: ${{ github.ref_type != 'tag' }}

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-java@v4
        with:
          distribution: temurin
          java-version: '21'
          cache: maven
      - name: Build and test
        run: mvn -B -ntp verify
      - uses: actions/upload-artifact@v4
        if: always()
        with:
          name: surefire-reports
          path: target/surefire-reports/
          if-no-files-found: ignore

  windows-portable:
    needs: test
    runs-on: windows-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-java@v4
        with:
          distribution: temurin
          java-version: '21'
          cache: maven
      - name: Package jar
        run: mvn -B -ntp -DskipTests package
      - name: jpackage app-image
        shell: pwsh
        run: |
          $app = "${{ github.event.repository.name }}"
          New-Item -ItemType Directory -Force -Path target/app | Out-Null
          Get-ChildItem target/*.jar -Exclude 'original-*' | Select-Object -First 1 | Copy-Item -Destination target/app/app.jar
          jpackage --type app-image --name $app --input target/app --main-jar app.jar --dest dist --java-options "-Dfile.encoding=UTF-8" --java-options "-Dsun.stdout.encoding=UTF-8" --java-options "-Dsun.stderr.encoding=UTF-8"
      - name: Zip portable folder
        shell: pwsh
        run: |
          $app = "${{ github.event.repository.name }}"
          Compress-Archive -Path "dist/$app/*" -DestinationPath "$app-windows-portable.zip" -Force
      - uses: actions/upload-artifact@v4
        with:
          name: ${{ github.event.repository.name }}-windows-portable
          path: ${{ github.event.repository.name }}-windows-portable.zip
      - name: Attach to release
        if: startsWith(github.ref, 'refs/tags/v')
        uses: softprops/action-gh-release@v2
        with:
          files: ${{ github.event.repository.name }}-windows-portable.zip
```

Правила сборки:
- `--type app-image` не требует WiX и даёт папку с EXE и встроенным рантаймом — это и есть тяжёлый переносимый exe. Типы `exe`/`msi` не использовать.
- `--main-class` не указывать: jpackage берёт `Main-Class` из манифеста, это работает и для shade-jar, и для Spring Boot.
- Консольной программе добавить `--win-console`.
- Windows-пакет собирается **только на windows-раннере**: jpackage не умеет кросс-сборку. Локально в Linux-песочнице его не запускать.
- Launch4j не использовать.
- Релиз: тег `vX.Y.Z` → workflow сам прикрепляет ZIP.

## 10.5 Проверка каркаса

Локально: `mvn -B -ntp verify` → Failures: 0, Errors: 0. Workflow проверяется запуском CI после пуша; результат зафиксировать в отчёте. Красный CI = фрагмент 000 не завершён.

# ЧАСТЬ 11. README.md

## 11.1 Кто и когда пишет

Первый кодер создаёт скелет README из ТЗ. Каждый владелец фрагмента, меняющий видимое пользователю поведение, дописывает свой раздел. Закрывающий кодер приводит README в полное соответствие реальному поведению программы.

## 11.2 Структура

Файл состоит из двух частей: **сначала полностью английская, затем полностью русская**. Русская часть — не сокращённый перевод, а полный эквивалент: те же разделы, те же примеры, тот же объём деталей.

Порядок:

1. `# Имя программы` — одна строка о том, что это.
2. Строка навигации: `[English](#english) | [Русский](#русский)`
3. `## English`
4. Разделы EN (таблица ниже)
5. `---`
6. `## Русский`
7. Те же разделы RU в том же порядке

| Раздел | Содержание |
|---|---|
| What it is / Что это | одно предложение без маркетинга |
| Who it is for / Для кого | конкретные роли и ситуации |
| Why / Зачем | какую проблему решает, чем лучше ручного способа |
| Features / Возможности | список того, что реально работает |
| Requirements / Требования | Windows 11 x64; Java **не нужна** — рантайм внутри папки |
| Download / Скачать | ссылка на Releases, имя ZIP, что внутри |
| Installation / Установка | распаковать ZIP в любую папку; установка не требуется; перенос копированием папки |
| Quick start / Быстрый старт | минимальный сценарий от запуска до результата, 5–7 шагов |
| User manual / Руководство пользователя | **подробно: каждый пункт меню, каждое поле, каждая кнопка, каждый флаг, каждый формат ввода и вывода, с примерами** |
| Examples / Примеры | реальные проверенные примеры вход → выход |
| Data storage / Хранение данных | какие файлы создаются, где, что можно копировать и переносить |
| Troubleshooting / Проблемы | таблица: симптом → причина → решение |
| FAQ / Вопросы | не менее 5 реальных вопросов |
| Limitations / Ограничения | чего программа не делает |
| Uninstall / Удаление | удалить папку |
| License / Лицензия | из репозитория, не выдумывать |

## 11.3 Правила разметки

- Только GFM. Из HTML разрешены `<details>`/`<summary>`.
- YAML-шапки в README нет.
- Один `#` на файл. Уровни заголовков не перескакивать.
- Пустая строка до и после списков, таблиц, блоков кода.
- У каждого блока кода указан язык: ` ```bash `, ` ```text `, ` ```java `.
- Таблицы: строка-разделитель обязательна, символ `|` внутри ячейки экранировать `\|`.
- Ссылки на файлы репозитория — только относительные. Ссылки на скачивание — на Releases.
- Скриншоты вставлять только если файл реально создан; выдуманных путей быть не должно.
- Никаких «и т.д.», «и прочее» в руководстве: либо описано, либо вынесено в «Ограничения».

## 11.4 Проверка README

Закрывающий кодер обязан: сверить состав разделов EN и RU (одинаковый), проверить каждую описанную команду и каждый пример на реальной программе, проверить все ссылки. Расхождение README с поведением = красный, ТЗ не закрывать.

# ЧАСТЬ 12. ФОРМАТЫ ФАЙЛОВ GVK

Все файлы `GVK/*.md` начинаются с md+ шапки: первая строка `---`, обязательные поля `id, file, etymology, desc, name, F, Q`, `id` = имя файла без расширения ≤ 17 знаков, ссылки в `R` только относительные. Разрешены GFM и `<details>/<summary>`. README.md — исключение, шапки не имеет. Тела файлов:

**PLAN.md** — таблица: `№ | пакеты | задачи ТЗ | наследие | готовность (команда) | оценка ч | TCP-порт | ci`

**STATE.md** — таблица: `№ | статус (свободен/в работе/готов/провален) | владелец | epoch | аренда до | ветка | последний зелёный`

**PORTS.md** — таблица: `порт | сигнатура | владелец № | зависимые №`

**LINKS.md** — список рёбер `№A → порт → №B`; ниже — порядок слияния.

**REQUESTS.md** — таблица: `заявка | порт | от № | к № | статус`

**AUDIT.md** — таблица: `файл | вердикт | обоснование | доказательство`

**claims/NNN.md** — поля: `owner, epoch, lease_until, packages, branch`

**reports/NNN.md** — поля: `status (ЗЕЛЕНО/КРАСНО), branch, last_green, tests, remaining`

**FINAL.md** — итог: слитые ветки, числа тестов, удалённый мусор, невыполненные пункты ТЗ, если есть.
