2. Рабочий каталог по C4, бутстрап по C3. Репозиторий пуст → создать начальный коммит в main. Прочитать ТЗ по C5, зафиксировать `tz_path` и `tz_sha`.

3. Аудит наследия. Опись всех исходников, базовая линия: собирается ли проект, какие тесты падают. Каждому файлу — вердикт в `GVK/AUDIT.md`:

| Вердикт | Когда | Доказательство |
| --- | --- | --- |
| KEEP | соответствует ТЗ или не противоречит | по умолчанию |
| REFACTOR | рабочее, но мешает границам фрагментов | что именно мешает |
| REWRITE | противоречит ТЗ или сломано | падающий тест или трассировка |
| DELETE | мёртвый код | вывод grep: ссылок нет; в ТЗ не упомянут |

Сохраняй лучшее, убирай худшее, не переписывай по вкусу. Нет доказательства — KEEP. Удаления только в ветке.

4. Фрагментация. Граница фрагмента = граница пакета, модуля или каталога принятого стека, пересечений файлов нет. Размер 5–15 файлов, ориентир один сеанс. Существующий код: число фрагментов ≈ ceil(исходники / 10), округляя вверх до границ пакетов. Новый проект: дробить по компонентам и пакетам из ТЗ, минимум один фрагмент разработки. Фрагмент 000 (каркас) существует всегда в программном репозитории; в документном репозитории каркас не создаётся.

Каждый фрагмент получает: номер, этап, пакеты, задачи ТЗ, наследие с вердиктами, критерий готовности точной командой, оценку часов, TCP-порт при необходимости, метку `ci: windows` для Windows-сборки или GUI. Нумерация сквозная (C8.4), номера не переиспользовать.

Карта путей — FILEMAP.md, грузи, если сомневаешься в размещении файла.

6. Реестр ролей. **Сначала выборы, потом публикация:** ветка `gvk-plan` создаётся push-ем по шагу 7 и только после её успеха создаётся `GVK/PEP.json` в main. Обратный порядок оставлял в main реестр без плана при отклонённом push. Создать реестр: `bin/pep.py init --repo O/R --tz <путь> --stack <язык> --kind code|doc --at <время GitHub> --out /tmp/PEP.json`, затем `api.py claim --role FIRST --path GVK/PEP.json --file /tmp/PEP.json --schema pep --no-guard` (бутстрап: реестра ещё нет, права берутся из шаблона). Подставить `repo`, `created_at` (время GitHub), `created_by`, `stage`, `tz_path`, `tz_sha`, `protocol_ver`, `limits`. Роли, для которых в этом репозитории нет дефицита (например PLANNER_TEST в документном репозитории), оставить в каталоге: каталог полон, дефицит считается по факту. Права не урезать и не расширять: они берутся из шаблона. Проверить обратным чтением и валидировать по схеме `pep`.

7. Ветка плана (выборы первого). Все файлы плана закоммитить в локальную ветку и выполнить до создания реестра:

```bash
git -c http.extraheader="$AUTH" push origin HEAD:refs/heads/gvk-plan
```

Создание ref атомарно: push прошёл — ты первый; отклонён — первый уже другой, читать его план и перейти к развилке C7. План и ветка появляются одновременно, окна гонки нет.

7.1. Выбор стека. По STACK.md ST2: требование ТЗ, затем наследие, затем пригодность под критерии ST1. Записать решение в `AUDIT.md` и `REPORT/stack.json` (язык, версия, упаковка, лицензии, чем закрыт каждый пункт ST1), проставить `stack` в `PEP.json`. Отказ от языка ТЗ запрещён (ST3).

Захватить `GVK/claims/000.md`, создать ветку `gvk/000` от main, выполнить SKELETON.md K1 (маркеры и файлы каркаса — из `stack.skeleton_by_stack[язык]`, права FIRST включают каркас любого стека) и файл своего стека (SKEL_JAVA.md K2/K4/K5, SKEL_PY.md K6/K7, SKEL_OTHER.md K8) и скелет README по README_SPEC.md, прогнать тесты. 9. Слияние 000. Первому разрешено слить `gvk/000` в main сразу (guard: `--merge --merge-fragment 000`, без номера фрагмента guard запрещает слияние FIRST): остальным нужен каркас. Только `git merge --no-ff origin/gvk/000` или `PUT /pulls/N/merge`. Запрещено создавать коммит через Git Data API с деревом другой ветки — это подмена содержимого, а не слияние. Проверка после слияния:

```bash
git ls-tree -r --name-only origin/main | grep -cE 'pom.xml|build.gradle|pyproject.toml|requirements.txt|\.csproj|go.mod|Cargo.toml|package.json|CMakeLists.txt|^(src|app|lib|cmd|internal|pkg)/'
git ls-tree -r --name-only origin/main | wc -l
```

Пусто или число файлов уменьшилось → слияния не было, немедленный `git revert`, отчёт, выход. Коммит, меняющий только `GVK/*.md`, слиянием не является. Проверка по маркерам своего стека обязательна: в v5.1 список был java-шным и давал ложное «слияния не было» для python-проекта с каталогом `app/`.
