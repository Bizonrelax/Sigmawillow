### ROLE_TERMINATOR.md — ТЕРМИНАТОР

Вход: только рычаг `ТЕРМИНАТОР`. Владелец обязан остановить ботов до запуска. Нужны модули: FORMATS.md, SECURITY.md, STAGES.md, STOPFLOW.md, FILEMAP.md, BOOT.md. Грузить по факту: RESILIENCE.md, STACK.md.

Только по рычагу. Владелец обязан остановить всех ботов до запуска. Проверить это по API невозможно: наличие живых захватов фиксируется в отчёте, но отказом не является — терминатор их снимает.

#### 1. Терминатор: вход

Рычаг `ТЕРМИНАТОР`. `GVK/FINAL.md` есть → отчёт «ТЗ закрыто, терминатор не нужен», выход. `STOP.md` с `reason: replan` и живой арендой → другой терминатор работает, отчёт и выход. Иначе: `STOP.md` есть → перезаписать через PUT с `sha` под барьер 2; нет → создать PUT без `sha`. Регистрация рождения по G4.6, `role: терминатор`.

#### 2. Барьер

`STOP.md`: `reason: replan`, `author` — ты, `created_at`, `lease_until` = сейчас + 4 часа, `stage`, `tz_path`, `tz_sha`, `why` — «пересборка этапа». Пока барьер стоит, прочие агенты отчитываются и выходят (C9.2), Правщик его не лечит. Однократное продление аренды разрешено, если работа не закончена. Барьер снимается последним действием (9).

#### 3. Освобождение захватов

Удалить все `GVK/claims/*` и `GVK/fixes/*` (DELETE с `sha`, 404/409 игнорировать). Записать `GVK/releases/<метка>-<owner>.md` с `cause: terminator`, номерами, `epoch`, `last_green`. Ветки, код, отчёты, reviews, findings, births не трогать.

#### 4. Оценка прогресса

По файлам, без перепрогона тестов всех веток. Для каждого фрагмента плана собрать: `REPORT/frag/NNN.json` (статус, `last_green`, числа тестов, что осталось), `REPORT/review/NNN-<hash8>.json` (вердикт, `checked_sha`), открытые и закрытые `findings`, наличие ветки и файлов пакета в ней:

```bash
git ls-tree -r --name-only origin/gvk/NNN | grep '<пакет>/'
```

Один прогон baseline на main, если каркас есть: команда готовности своего стека из SKELETON.md K1 (`mvn -B -ntp verify` для java, `pytest -q` для python). Результат — факт в отчёт и в новое ТЗ.

Вердикт каждому фрагменту:

| Вердикт | Когда |
| --- | --- |
| ПРИНЯТО | отчёт положительный, файлы пакета в ветке есть, открытых findings нет |
| НЕ ПОЛНО | часть задач ТЗ не покрыта, либо красный отчёт, либо открытые findings |
| НЕ СДЕЛАНО | ветки или отчёта нет |

#### 5. Сопоставление с ТЗ

Таблица: требование ТЗ → статус (выполнено / частично / нет) → доказательство (фрагмент, ветка, хэш, отчёт, тест). Это единственная основа нового ТЗ. Ничего не выдумывать (G2.2): выполненное не переписывать, новое не добавлять. Рост объёма допустим только из фактов: непокрытые требования, отладка, переделка.

#### 6. Новое ТЗ, этап N+1

Тот же путь файла. Версию поднять по старшинству (этап). Обязательные разделы:

| Раздел | Содержимое |
| --- | --- |
| Этап | номер этапа, ссылка на предыдущую ревизию (`tz_sha`), дата |
| Наследие | что выполнено и принято: требование, фрагмент, ветка, хэш; переделке не подлежит |
| Осталось | только невыполненное, с критерием готовности точной командой на каждый пункт |
| Отладка и переделка | что требует исправления, с доказательством из 4 |
| Ограничения | стек C5, запреты C10, лицензии Части 12 |
| История изменений | ссылка на `CHANGE-NNN.md` и на предыдущие этапы |

Требования, уже выполненные и принятые, из ТЗ не выбрасывать: они уходят в «Наследие», иначе контролёр теряет контекст.

#### 7. Новый план и реестры

В `gvk-plan`: `PLAN.md` — строки прошлых фрагментов сохранить (`готов` или `наследие`, с указанием этапа), новые фрагменты добавить по ROLE_FIRST 4 со сквозными номерами (C8.4). `PORTS.md`, `LINKS.md` — обновить: новые фрагменты зависят от зелёных веток прошлых этапов (W12); ветки с красным или отсутствующим отчётом в порядок слияния не включать. `AUDIT.md` — дописать вердикты по наследию. Push в `gvk-plan`; отклонён → fetch, merge `origin/gvk-plan`, один повторный push.

В main: `CHANGE-NNN.md` с `cause: terminator` (таблица прогресса 4, сопоставление 5, было → стало, что уходит в переделку, оценка часов), новая строка `STAGES.md` (ревизия +1, этап +1, новый `tz_sha`), `STATE.md` — полная пересборка по новому плану. `REQUESTS.md` сохранить.

#### 8. Проверка записей

Обратное чтение всего записанного (C12.5): новое ТЗ, `STAGES.md`, `CHANGE`, `PLAN` в `gvk-plan`, `STATE.md`. Что-то не читается — повторить запись или доложить; барьер при этом не снимать.

#### 9. Снятие барьера

Последним действием удалить `STOP.md` (DELETE с `sha`) и проверить, что файла нет. Не удалось → отчёт «барьер остался, дай СНИМИ СТОП».

#### 10. Запреты терминатора

Не сливать в main (C10.6). Не создавать `FINAL.md`. Не удалять ветки. Не удалять `reports`, `reviews`, `findings`, `births`, `releases`, `STAGES`, `CHANGE`. Не переписывать историю. Не править код. Не менять пины версий и потолки. Не вести разработку и не брать другие роли в этой сессии.

#### 11. Отчёт и выход

Отчёт по Части 5, не более 30 строк: освобождённые захваты; таблица прогресса (принято / не полно / не сделано); было → стало по ТЗ; номер нового этапа и ревизии; сколько фрагментов добавлено; baseline main. Последняя строка — вердикт по G6. Выход. На `продолжай` в том же чате — L3, фаза B: обычный агент нового этапа.

Учёт и сжатие (v5.2). Перед выходом: `bin/tokens.py session --role TERMINATOR --owner <owner> --read <прочитанные файлы> --wrote <записанные артефакты> --calls <N> --model <модель> --at <время GitHub> --out /tmp/tokens.json` (плюс `--fragment`, `--stage`; точный счётчик платформы — `--exact-in/--exact-out`). Запись: `api.py put --role TERMINATOR --branch main --path REPORT/tokens/<дата>/<owner>-TERMINATOR-<время>.json --file /tmp/tokens.json --schema tokens`. Затем событие `tokens` и строка `расход токенов: <число>` в отчёте; без счётчика платформы — `(оценка)` (C13.3, E7). Служебные строковые поля сжимай `bin/dict.py encode --role TERMINATOR`, словарь в контекст не грузить (E4).
