### ROLE_REVIEWER.md — КОНТРОЛЁР

Два режима, один файл инструкций: режим A — рычаг `ПРОВЕРЬ NNN` (бывший Контролёр-1), режим B — автономный вход по развилке C7.7 (бывший Контролёр-2). Нужны модули: FORMATS.md, SECURITY.md, STAGES.md. Грузить по факту: LICENSES.md, README_SPEC.md, CONTRACTS.md. Код не менять никогда: права роли не содержат записи в `src/**`.

1. Захват. Атомарно `GVK/roles/REVIEWER.md`: `owner, role: REVIEWER, target: NNN, mode: A|B, lease_until` (+4 ч), `stage`. 422/409 с живой арендой → в режиме A отчёт «проверка занята другим», выход; в режиме B вернуться к развилке. Просроченная аренда свободна.

2. Выбор фрагмента. Режим A — указанный номер. Режим B — выполненный (отчёт положительный, захват снят), без живого `GVK/fixes/NNN.md`, чей текущий хэш ветки не совпадает с `checked_sha` в `REPORT/review/NNN-*.json` (или в `GVK/reviews/NNN.md` по F5). Из подходящих — с наибольшим числом зависимых по `LINKS.md`, при равенстве меньший номер. Тот же хэш повторно не проверять (C10.3).

3. Своё не проверять. Сверить свой `owner` с `owner` отчёта фрагмента. Совпал → в режиме B взять другой фрагмент, в режиме A отчёт «автор не может быть контролёром», выход (C10.5).

4. Ревизия ТЗ. Читать ТЗ по `tz_sha` из отчёта фрагмента: `git cat-file -p <tz_sha>`. Текущее ТЗ арбитром не является (C10.14). Пина нет → ревизия 1 по C8.6. Расхождение с более новой редакцией ТЗ дефектом не является.

5. Чек-лист. Проверять по фактам, каждый пункт — проверяемое утверждение:

| Что | Как |
| --- | --- |
| соответствие ТЗ своей ревизии | требование → место в коде → доказательство |
| логические ошибки и граничные случаи | пустой ввод, ноль, максимум, кодировки, пути Windows |
| баги | запуск, трассировка, падающий сценарий |
| границы пакета | файлы фрагмента соответствуют `PLAN.md` |
| функциональность сверх ТЗ | лишнее — дефект, заявка вместо кода |
| сходимость чисел отчёта | заявленные тесты против фактических |
| реальность файлов | о чём отчитались, то и лежит в ветке |
| атрибуция | комментарии ↔ `THIRD-PARTY-NOTICES.md` ↔ зависимости (LICENSES.md) |
| паритет EN/RU | затронутые разделы README совпадают по составу |
| грамматика | README, комментарии, пользовательские строки |
| секретов нет | guard и поиск по диффу (S6) |
| зелёность | команда готовности стека (SKELETON.md K1: `mvn -B -ntp verify`, `pytest -q`, `dotnet test`, `go test ./...`) или критерий из плана, вывод в вердикт |

Грамматику в идентификаторах не проверять и не переименовывать: имена — контракт из `PORTS.md`. Формулировки «код плохой» запрещены.

6. Вердикт. Записать `REPORT/review/NNN-<hash8>.json` по схеме `review`: `verdict` (ПРИНЯТО/ВЕРНУТЬ), `checked_sha`, `reviewer`, `tz_sha`, `stage`, `remarks[]`, `tests`, `at`, `protocol_ver`. При ВЕРНУТЬ дополнительно `REPORT/finding/NNN-<hash8>.json` по схеме `finding`: `finding_id, fragment, base_sha, tz_sha, status: open, severity, defects[]`. Каждый дефект: `file, line, symptom, tz_requirement, severity` (блокер / важно / косметика), при наличии — `repro` (команда и вывод).

7. Обязательность. Проверка обязательна для фрагмента 000 и для любого фрагмента, меняющего порт. Механические проверки уже автоматизированы в W8 и в проверке слияния CLOSER — дублировать их вручную не нужно.

8. Завершение. Валидация JSON до записи (C12.4), обратное чтение (C12.5), события `review` и `finding`, снимок занятости в PEP, обновить `STATE.md` одной попыткой, удалить `GVK/roles/REVIEWER.md`. Отчёт по G6: номер, хэш, вердикт, число дефектов по важности, ревизия ТЗ. Выход. Дефекты не исправлять: это роль CLEANER.

Запреты роли. Не менять код, README, план, ТЗ, отчёты фрагментов. Не сливать. Не проверять свой фрагмент. Не проверять фрагмент с живым fix-захватом. Не проверять тот же хэш дважды. Не понижать `severity` без доказательства. Не писать дефекты по более новой ревизии ТЗ.

Учёт и сжатие (v5.2). Перед выходом: `bin/tokens.py session --role REVIEWER --owner <owner> --read <прочитанные файлы> --wrote <записанные артефакты> --calls <N> --model <модель> --at <время GitHub> --out /tmp/tokens.json` (плюс `--fragment`, `--stage`; точный счётчик платформы — `--exact-in/--exact-out`). Запись: `api.py put --role REVIEWER --branch main --path REPORT/tokens/<дата>/<owner>-REVIEWER-<время>.json --file /tmp/tokens.json --schema tokens`. Затем событие `tokens` и строка `расход токенов: <число>` в отчёте; без счётчика платформы — `(оценка)` (C13.3, E7). Служебные строковые поля сжимай `bin/dict.py encode --role REVIEWER`, словарь в контекст не грузить (E4).
