# Запуск роя на Bizonrelax/PrimeWalker-2 — пошагово

Ти, это план под то состояние репозитория, которое видно на твоих скриншотах: `main`, java-проект (`pom.xml`, `src/`), релиз v1.0.0, `docs/`, загруженный `GVK_PROTOCOL/`, `REPORT/events/` и один свежий файл `GVK/roles/FIREFIGHTER.md`. Реестра `GVK/PEP.json` и ветки `gvk-plan` в `main` нет — значит **рой ещё не инициализирован**, и первой должна быть роль FIRST, а не ПОЖАР.

## 0. Что произошло на самом деле

Ты дал рычаг `ПОЖАР`. Это роль FIREFIGHTER — разбор пожара: пересборка уже существующего плана, когда документация разошлась с кодом. Она не пишет код и не создаёт план с нуля. Агент захватил роль, дошёл до обязательного шага «рождение» и получил запрет guard: путь `GVK/births/**` стоял в запрещённых для этой роли. Это **дефект моего протокола**, не агента и не твой ошибки: процедура входа требовала того, что матрица прав запрещала. Он назван D58 и исправлен в поставке 5.2.1.

Второе: даже без дефекта ПОЖАР на неинициализированном репозитории — пустая трата сессии. Теперь FIREFIGHTER на первом же шаге проверяет наличие реестра и плана и, если их нет, отчитывается «нужен FIRST» и выходит (D60).

## 1. Обнови протокол в репозитории (5 минут)

1. Скачай `GVK_v5.2.zip` из рабочей области, распакуй.
2. В GitHub удали старую папку `GVK_PROTOCOL/` в `main` (или замени её содержимое целиком) и загрузи содержимое распакованной папки `GVK_v5.2/` как `GVK_PROTOCOL/`. Внутри должны лежать `PROTOCOL.md`, `MANIFEST.json`, `GUIDE.md`, `CHANGELOG.md`, `SELFTEST.md` и папка `GUIDEGVK/`.
3. Коммить в `main`. Протокол агентам только чтение — править его они не имеют права.

Проверка у себя на компьютере (нужны только `git` и `python3`):

```bash
cd GVK_v5.2
python3 GUIDEGVK/bin/selftest.py          # 141/141 за ~5 c
python3 GUIDEGVK/bin/doctor.py --root .   # 22/22
python3 GUIDEGVK/bin/manifest.py --check  # MANIFEST OK
```

Если грузил через веб-интерфейс GitHub и что-то потерялось — `manifest.py --check` покажет `MISMATCH` со списком файлов. Это ровно та проверка, которую агент делает на входе: повреждённый протокол он не исполняет.

## 2. Убери зависший захват

В `main` остался `GVK/roles/FIREFIGHTER.md` от прерванной сессии. Он держит роль 8 часов. Два варианта:

- быстро: удали этот файл в веб-интерфейсе GitHub (ты владелец, тебе можно);
- по протоколу: в новом чате отправь `РЫЧАГ: ТЕРМИНАТОР 2` — снимет все захваты, код и отчёты не тронет.

FIRST этот файл не мешает, но лучше убрать, чтобы состояние было чистым.

## 3. Первая сессия: FIRST, без рычага

Новый чат Qwen-Coder. **В селекторе выбери репозиторий `Bizonrelax/PrimeWalker-2` и ветку `main`** — без этого кодер уходит в режим «сделать сайт» и протокол не работает. Отправь:

```text
Токен: <твой fine-grained PAT>
Репозиторий: Bizonrelax/PrimeWalker-2
Протокол: GVK v5.2.1, папка GVK_PROTOCOL/ в этом же репозитории. Не получен — ничего не менять, доложить и выйти.
ТЗ: docs/TZ.md
```

Никаких рычагов в первом сообщении. Роль агент определит сам: нет `PEP.json` и `gvk-plan` → он FIRST.

Что он должен сделать за сессию: опись наследия с вердиктами (`GVK/AUDIT.md`), выбор стека, план фрагментов (`GVK/PLAN.md`), реестры портов и связей, потолки, журнал ревизий, ветку `gvk-plan`, реестр ролей `GVK/PEP.json`, каркас фрагмента 000 и его слияние в `main`, отчёт с `СОСТОЯНИЕ: ЗЕЛЕНО` и строкой `расход токенов: N`.

Признак успеха в репозитории: появились `GVK/PEP.json`, `GVK/PLAN.md`, ветка `gvk-plan`, зелёный CI по каркасу.

## 4. Дальше: одинаковые сообщения в новых чатах

Каждая новая сессия — тот же текст, что в шаге 3, без рычагов. Агент сам посмотрит срез состояния и возьмёт то, что нужно: свободный фрагмент (DEV), проверку готового (REVIEWER), исправление дефекта (CLEANER), тест-план (PLANNER_TEST), тесты (TESTER), релиз или закрытие (CLOSER).

Сколько свободных фрагментов в плане — столько чатов можно запустить параллельно. Захваты атомарные: два агента на один фрагмент не сядут, проигравший возьмёт следующий.

В том же чате, если агент закончил свою роль, можно писать просто `продолжай` — он доделает своё или войдёт новичком.

## 5. Рычаги, которые тебе реально понадобятся

Рычаг — отдельная строка, начинающаяся с `РЫЧАГ:`. Без этого слова это просто текст задачи.

| Сообщение | Что делает |
| --- | --- |
| `РЫЧАГ: ТОЛЬКО ОТЧЁТ` | дешёвая сводка состояния: что занято, что готово, что красное |
| `РЫЧАГ: РАСХОД` | сколько токенов сожжено, по ролям и моделям, сколько измерено точно |
| `РЫЧАГ: ПРОДОЛЖИ 003` | доделать конкретный фрагмент |
| `РЫЧАГ: ПРОВЕРЬ 003` | проверка фрагмента ревьюером |
| `РЫЧАГ: ТЕСТ` | тест-план и прогоны |
| `РЫЧАГ: ТЕРМИНАТОР 2` | снять зависшие захваты, ничего не ломая |
| `РЫЧАГ: СОРЕЛ` | промежуточный релиз, рой продолжает работать |
| `РЫЧАГ: ЗАКРОЙ` | финальное закрытие: приёмка, `FINAL.md mode: close`, уборка |
| `РЫЧАГ: ПОЖАР` | только когда план уже есть и разошёлся с документацией |

## 6. Как «заставить» кодера писать программу

Честно: заставить нельзя, и не нужно. Протокол устроен так, что каждая сессия сама находит работу по состоянию репозитория. Твоя роль — запускать сессии и читать отчёты. Программа получается из цикла:

1. FIRST один раз создаёт план и каркас.
2. Дальше сессии берут фрагменты и пишут код, пока план не кончится.
3. Проверка и тесты закрывают дефекты, CLEANER чинит.
4. CLOSER собирает релиз и закрывает проект.

Что реально ускоряет цикл:

- **Параллельность.** Три свободных фрагмента — три чата одновременно. Это главный рычаг скорости.
- **Точное ТЗ.** Агент не имеет права додумывать функциональность сверх ТЗ: всё лишнее уходит в заявку `GVK/REQUESTS.md`. Чем конкретнее `docs/TZ.md` (критерии готовности, команды запуска, что считается «готово»), тем меньше пустых сессий.
- **Критерий готовности командой.** В плане у каждого фрагмента должна быть точная команда проверки (`mvn -B -ntp verify`, `pytest -q`). Тогда «зелёно» — это факт, а не мнение агента.
- **Не вмешиваться в середину.** Если агент работает, второй такой же роли на тот же фрагмент не запускай: захват не пустит, сессия сгорит впустую.

Если хочешь совсем без ручных чатов — тот же текст запуска можно отправлять программно через API Qwen-Coder в цикле: одна итерация = одна сессия = один фрагмент. Протокол к этому готов: состояние живёт в репозитории, а не в памяти чата.

## 7. Если снова остановится

Читай причину в отчёте и различай три случая.

1. **Запрет по правам на чужое** (чужой пакет, каркас, ТЗ, слияние) — так и надо. Запусти следующую сессию, работу возьмёт нужная роль.
2. **Запрет на то, что протокол сам требует** (как D58 с рождением) — дефект протокола. Пришли мне отчёт целиком, я поправлю матрицу и пересоберу поставку. Разовый обход — рычаг `ДОСТУП` с записью `GVK/ACCESS.md` в `main` (адресат, срок, твоё подтверждение). Не выдавай права навсегда и не разрешай агенту править протокол.
3. **«Модуль не поставлен» / `MANIFEST MISMATCH`** — протокол загружен не целиком. Перезалей папку и проверь `manifest.py --check`.

Полезная привычка: после каждой сессии смотреть `РЫЧАГ: ТОЛЬКО ОТЧЁТ`. Это дешёвая сессия наблюдателя, она ничего не меняет и показывает, где рой стоит.
