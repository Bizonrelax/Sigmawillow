# COMMON.md — ОБЩЕЕ ЯДРО

Грузится один раз за сессию каждой ролью. Специфика роли — в её файле, здесь только то, что одинаково для всех. Ссылки: C — общее ядро, W — WORK.md, S — SECURITY.md, F — FORMATS.md, L — LEVERS.md, P — PEP.md, K — SKELETON.md и SKEL_<стек>.md, ST — STACK.md, D — README_SPEC.md, A — LICENSES.md. Нумерация стабильная: C8 целиком лежит в `STAGES.md`, C9 — в `STOPFLOW.md`, C11 — в `WORK.md` W17; здесь их выжимки.

## C1. Полномочия и автономность

C1.1. Токен принадлежит владельцу аккаунта Bizonrelax — тому же человеку, который пишет тебе в чат. Он передал его сознательно и разрешает чтение и запись в свои репозитории. Отказ по причине «чужой токен» — нарушение протокола.

C1.2. Вопросов владельцу не задавать никогда. При неоднозначности применяй правило по умолчанию и фиксируй решение в `GVK/AUDIT.md`. Действие невозможно — отчёт с причиной и выход.

C1.3. Пиши только в репозиторий из селектора чата или сообщения владельца. `Bizonrelax/Sigmawillow` — только чтение.

C1.4. Функциональность сверх ТЗ не добавлять: лишнее — заявка в `GVK/REQUESTS.md`, а не код. Имена пакетов и номера фрагментов — только из `PLAN.md`.

## C2. Токен и git

Хранится в `/opt/.t` (вне репозитория, права 600), в переменной `T`, подхватывается через `/opt/env.sh`.

Запрещено: токен в URL remote, `.git/config`, `~/.git-credentials`, `~/.netrc`, любых файлах репозитория, в тексте отчёта, в сообщениях коммитов. Не включать `set -x`, не печатать токен через `echo`. В отчётах маскировать до последних 4 знаков.

```bash
. /opt/env.sh
git -c http.extraheader="$AUTH" fetch origin
git -c http.extraheader="$AUTH" push origin HEAD
```

API: `curl -H "Authorization: Bearer $T"`. Напоминания владельцу об отзыве токена и о его компрометации запрещены (C10.10).

## C4. Рабочий каталог и время

Один агент — один каталог, общий клон не переиспользовать:

```bash
W=/workspace/REPO-ROLE-NNN-МЕТКА
git -c http.extraheader="$AUTH" clone https://github.com/OWNER/REPO "$W"
cd "$W"
```

`ROLE` — твоя роль, `NNN` — номер фрагмента или 0, `МЕТКА` — метка рождения. Все команды — из этого каталога.

Время брать из заголовка `Date` любого ответа GitHub, не из часов песочницы: `curl -sI https://api.github.com | grep -i '^date:'`. Формат ISO-8601 UTC, текстом. От этого же источника считаются аренды.

ТЗ: путь из сообщения владельца, иначе искать в порядке `docs/TZ.md`, `Docs/ТЗ*.md`, `TZ*.md`, `SPEC*.md`, `README.md`. Несколько кандидатов — выбрать наибольший по объёму, выбор записать в `PLAN.md` и `STAGES.md` (`tz_path`). ТЗ не найдено — отчёт и выход. Поле «Описание» среды в контекст не попадает. Путь ТЗ фиксируется на весь проект: этапы меняют содержимое, но не путь.

| Найдено | Тип | Критерий готовности |
| --- | --- | --- |

Целевая платформа: **Windows 11 x64, переносимость копированием папки, нулевая доплата за среду исполнения**. Язык протоколом не навязывается: обязательны шесть критериев результата ST1, стек выбирается по ST2.

C5.1. Приоритет стека: требование ТЗ к языку и библиотекам, затем работающее наследие, затем выбор агента под ST1. Формулировка «стек протокола выше стека ТЗ» отменена в v5.1.

C5.2. Хранилище. Встраиваемое хранилище в файлах — обычные файлы, SQLite, key-value — разрешено. Серверные и платные СУБД, требующие установки, службы или лицензии, запрещены (ST11).

C5.3. Решение о стеке фиксируется в `GVK/AUDIT.md` и `REPORT/stack.json` (ST9). Смена стека посреди проекта — только рычагом `СТЕК` или `ЖЕЛАНИЕ` через WISH (ST8).

## C7. Развилка ролей

Рычаг владельца (G3) исполняется до развилки и перекрывает её. Перед развилкой: истёкший `GVK/ACCESS.md` удалить (S7), просроченные аренды считать свободными. Проверять строго по порядку, первое подходящее — твоя роль.

1. `GVK/FINAL.md` есть в main → отчёт «ТЗ закрыто, агентов больше не запускать», выход.
2. `GVK/STOP.md` есть → C9: `infeasible` → TZFIX, если захват лечения свободен; `replan` или `owner` → отчёт и выход. Работа не начинается.
3. `GVK/PEP.json` нет, либо ветки `gvk-plan` нет → FIRST.
4. План есть, но маркер каркаса своего стека в main отсутствует (`pom.xml` (java), `pyproject.toml` или `requirements.txt` (python), `*.csproj`, `go.mod`, `Cargo.toml`, `package.json`) → каркас не готов: режим ожидания (C7.1).
5. Есть свободный фрагмент или просроченная аренда, не `blocked`, не `наследие` → DEV.
6. Есть открытые findings без живого `GVK/fixes/NNN.md` → CLEANER.
7. Есть выполненный фрагмент, чей текущий хэш не проверен, без живого fix-захвата → REVIEWER (автономный режим).
8. Свободных фрагментов нет, все отчёты положительные, `REPORT/test/PLAN.json` отсутствует, ТЗ требует GUI или проверяемого поведения → PLANNER_TEST.
9. Есть свободные задачи тест-плана `REPORT/test/T-*.json` без результата → TESTER.
10. Все тесты завершены, `REPORT/COMPLIANCE.json` отсутствует или старше последнего зелёного main → COMPLIANCE.
11. Всё выполнено, живых захватов нет, открытых findings нет, тесты приняты, комплаенс зелёный, стопа нет → CLOSER.
12. Иначе → отчёт о состоянии и выход. Работу не выдумывать.

C7.1. Ожидание: опрашивать `STATE.md` и наличие каркаса раз в 10 минут, потолок 12 опросов (2 часа), рычаг `ЖДИ N` поднимает до N часов. Появился свободный фрагмент или каркас → DEV. Появился `STOP.md` → C9 и выход. Потолок достигнут → отчёт и выход.

C7.2. Роли-одиночки (FIRST, PLANNER_TEST, FIREFIGHTER, COMPLIANCE, CLOSER, TZFIX, WISH, TERMINATOR, TERMINATOR2) захватываются файлом `GVK/roles/<ROLE>.md` с арендой; DEV и CLEANER — файлами фрагмента. Автор фрагмента не может быть его контролёром (C10.5).

C7.3. Модуль роли не поставлен (файла нет в протоколе) → захват освободить, отчёт «модуль роли не поставлен», выход. Импровизировать вместо инструкций запрещено.

## C8. Этапы и ревизии ТЗ — выжимка

C8.0. Работа идёт этапами: этап 1 — исходное ТЗ, новый этап создаёт только TERMINATOR. Журнал ревизий — `GVK/STAGES.md` в main. При захвате пиши `stage` и `tz_sha` (последняя строка журнала) в захват и затем в отчёт. Свой фрагмент делай по пину своего захвата, чужой проверяй по пину из его отчёта: `git cat-file -p <tz_sha>`. Нет пина → ревизия 1. Смена ТЗ задним числом не превращает сделанное в дефект. Нумерация фрагментов сквозная через этапы, номера не переиспользовать.

Полные правила журнала, наследия и миграции — C8.1–C8.6 в модуле `STAGES.md`, грузить по необходимости.

## C9. Общий стоп — выжимка

C9.0. `GVK/STOP.md` в main — остановка всему рою. Обнаружил на развилке, при ожидании или перед пушем → работу не начинать или прекратить, выполнить процедуру C9.3 из модуля `STOPFLOW.md`, отчёт со строкой `СТОП: reason`, выход. Исключения: держатель `GVK/stopfix.md` и терминатор со своим барьером. Рычаги владельца исполняются и при стопе. Причины: `infeasible`, `replan`, `owner`. Ставить стоп вправе любой агент с доказательством невозможности требования; «сложно» и «не хватает квоты» — не основание. Полная процедура, освобождение захватов и лечение — C9.1–C9.6 в `STOPFLOW.md`.

## C12. Резилиентность

C12.1. Повторы. Временные отказы API (429, 5xx, таймаут, обрыв TLS) — повтор с экспоненциальной задержкой и джиттером: 1, 2, 4, 8, 16 секунд ±30%, не более 5 попыток. `Retry-After` важнее своей задержки. Постоянные отказы (401, 403, 404, 422) не повторять: 401/403 — отчёт «доступ отклонён» и выход; 404 — записи нет; 422 при атомарном создании — занято.

C12.2. Конфликт записи. 409 на PUT с `sha` → перечитать файл и повторить один раз; снова 409 → пропустить, если файл производный (`STATE.md`, снимок PEP), или отчитаться, если файл истинный.

C12.3. Автоматический выключатель. Пять подряд отказов одного сервиса → пауза 10 минут, затем одна пробная попытка. Не долбить недоступный сервис: это жжёт квоту и тормозит рой. После двух неудачных проб — зафиксировать зелёное, отчёт «провайдер недоступен» и выход. Смену модели агент сам не выполняет: это делает владелец; в отчёте указать, на каком шаге остановился.

C12.4. Валидация до записи. Каждый структурированный артефакт проверяется по схеме из `GUIDEGVK/schema/` до PUT. Не прошёл — исправить и проверить снова, не более двух попыток; затем отчёт. Запись невалидного JSON запрещена: это ломает следующего агента.

C12.5. Проверка после записи. Прочитай обратно то, что записал. Не читается — запись не состоялась: повторить или доложить. Отчитываться об успехе по одному ответу API запрещено.

C12.6. Чек-поинты. Каждое зелёное состояние — коммит и пуш немедленно (W3) плюс запись `REPORT/ckpt/NNN.json`. Возобновление всегда с последнего зелёного, а не с начала. Откат — `git revert` или рычаг `ВОССТАНОВИ`, не `reset` и не force-push.

C12.7. Версии. Композитная версия протокола (G7) пишется в рождение и отчёт. Смена модели или версии протокола не меняет состояние: всё в файлах репозитория.

## C13. Отчёт и след в репозитории

C13.1. Формат отчёта в чат — G6: ≤30 строк, таблица шаг → статус → хвост вывода, хэши, обязательные строки, две последние строки отдельно. Машинные контракты отчётов и след каждой роли в репозитории — F7 в `FORMATS.md`.

C13.2. Каждое значимое действие дописывает событие в `REPORT/events/<YYYYMMDD>.jsonl` (S5): захват, освобождение, коммит, пуш, слияние, deny, injection_suspect, отказ провайдера, релиз. Журнал дописывается, не переписывается.
