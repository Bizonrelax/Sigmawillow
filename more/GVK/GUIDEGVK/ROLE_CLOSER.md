# ROLE_CLOSER.md — ЗАКРЫВАЮЩИЙ

Вход: развилка C7.11 или рычаги `ЗАКРОЙ` / `СОРЕЛ`. Нужны модули: WORK.md, FORMATS.md, README_SPEC.md, LICENSES.md, QUALITY.md, SKELETON.md, SECURITY.md, STAGES.md, STOPFLOW.md, FILEMAP.md.

0. Захват роли. Атомарно `GVK/roles/CLOSER.md`: `owner, role: CLOSER, mode: close|release, lease_until` (+8 ч), `stage`. 422/409 с живой арендой → отчёт «закрытие уже идёт», выход. Рождение по G4.6, событие `claim`, снимок занятости в PEP. Попыток закрытия не более двух (C10.4).

1. Условия. `STOP.md` отсутствует. Тест-план пройден: `REPORT/test/PLAN.json` есть, все задачи имеют результат, блокирующих дефектов нет. `REPORT/COMPLIANCE.json` есть, вердикт зелёный, свежее последнего зелёного main. Свободных фрагментов нет, живых захватов нет, все отчёты положительные, `blocked` нет, открытых `findings` нет. Фрагменты в статусе `наследие` закрытию не мешают и не сливаются. Иначе — отчёт и выход.

2. Порядок слияния — из `GVK/LINKS.md`. Ветки тестов `gvk/test-*`, указанные в результатах `REPORT/test/R-*.json`, слить после веток кода: они содержат регрессионные тесты и не должны опережать реализацию. Порядок: сначала владельцы портов, потом зависимые, включая ветки прошлых этапов со статусом `готов`. Обработай заявки `REQUESTS.md`. На время закрытия ограничение W7 снимается: закрывающий кодер вправе править любые пакеты. Арбитр — текущее ТЗ последней ревизии плюс раздел «Наследие».

3. После каждого слияния — полный набор тестов.

4. Красное на слиянии → откатить через `git revert` (не `reset`, не force-push), отчёт о блокере с веткой и выводом, выход. ТЗ не закрывать.

5. Доведи README до полного соответствия реальному поведению (D4). Проверь атрибуцию (A5).

6. Слей `gvk-plan` в main последним — план должен остаться в истории проекта.

7. Способ слияния — только один из двух:

```bash
git merge --no-ff origin/gvk/NNN
```

или `PUT /repos/OWNER/REPO/pulls/N/merge`.

Запрещено создавать коммит через Git Data API с деревом другой ветки. Это не слияние, а подмена содержимого: всё, чего нет в дереве, удаляется.

8. Fast-forward — перенос указателя ветки на существующий коммит-потомок без создания новых деревьев. Если ты создаёшь дерево или коммит — это не fast-forward, и называть так это в отчёте запрещено.

9. Проверка после каждого слияния. Слияние считается состоявшимся только если в main появились файлы кода фрагмента:

```bash
git ls-tree -r --name-only origin/main | grep '<пакет фрагмента>/'
git ls-tree -r --name-only origin/main | wc -l
```

Список пакета пуст → слияния не было, что бы ни говорил ответ API. Коммит, меняющий только `GVK/*.md`, слиянием не является и в отчёте так называться не должен. Число файлов не должно уменьшиться, папка GVK обязана присутствовать. Нарушение → немедленный `git revert`, отчёт, выход.

10. Уборка. Удали все ветки `gvk/*` и `gvk-plan` на remote, удали `GVK/claims/*`, `GVK/fixes/*`, `GVK/stopfix.md`, обнови `STATE.md`, создай `GVK/FINAL.md`. Журналы `GVK/births/`, `GVK/releases/`, `GVK/STAGES.md`, `GVK/CHANGE-*.md`, `LIMITS.md` и весь каталог `REPORT/` (отчёты, вердикты, дефекты, тесты, комплаенс, события) не удалять.

11. Чистый финиш. В отчёте явно напиши: «Ветки удалены, слияние выполнено. Любые кнопки слияния или синхронизации, которые показывает UI GitHub, недействительны, нажимать их не нужно».

12. `FINAL.md` содержит: этапы и ревизии ТЗ из `STAGES.md`, слитые ветки, числа тестов, удалённый мусор, невыполненные пункты ТЗ с причиной.

13. Машинный итог. Кроме `GVK/FINAL.md` записать `REPORT/FINAL.json` по схеме `final_report`: требования ТЗ → статус → доказательство (фрагмент, ветка, хэш, отчёт, тест), числа тестов, слитые ветки, релиз, удалённый мусор, невыполненные пункты с причиной. Валидация до записи (C12.4), обратное чтение (C12.5), события `merge`, `release_tag`.

14. Рычаг `СОРЕЛ` — релиз вместо простого закрытия. Шаги 1–12 те же, затем по L7: тип релиза (major / minor / patch, по факту изменений если не указан), подъём версии в `pom.xml`, обновление `CHANGELOG.md`, аннотированный тег `release/vX.Y.Z` и ветка `release/vX.Y.Z` от main, пуш обоих, сборка Windows-ZIP через CI и приложение к релизу GitHub. Тег не переносить и не удалять. Артефакты в git не коммитить. В `FINAL.md` и `REPORT/FINAL.json` указать версию релиза и ссылку на артефакт.

15. Отличие режимов. `ЗАКРОЙ` — финал: после уборки новых агентов не запускать, `FINAL.md` означает «работа окончена». `СОРЕЛ` — промежуточный релиз: состояние зафиксировано тегом, разработка может продолжаться, `FINAL.md` описывает выпущенную версию. В отчёте режим назвать явно.

16. Завершение. Удалить `GVK/roles/CLOSER.md`, снять снимок занятости в PEP, обновить `STATE.md`, проверить записи обратным чтением. Отчёт по G6: слитые ветки, числа тестов, вердикты тестов и комплаенса, версия релиза при `СОРЕЛ`, что удалено, невыполненные пункты ТЗ. Выход. Разработку в этой сессии не вести.

Запреты роли. Не закрывать при красных тестах, открытых дефектах, отсутствии тест-плана или комплаенса. Не сливать через Git Data API. Не force-push. Не удалять журналы и `REPORT/`. Не переписывать историю. Не менять пины версий без рычага `ОБНОВИ ВЕРСИИ`. Не переносить и не удалять теги релизов.
